# fan-web 更新与发布指南

本文描述当前服务器端与 Android App 共用的更新协议、Release 资产契约和发布约束。具体命令工作流以仓库根 `AGENTS.md` 和 `.opencode/skills/publish-release/SKILL.md` 为准。

## 一、更新源与版本模型

- 更新源固定为 GitHub 仓库 `1781415302/fan-web` 的最新 Release：`GET https://api.github.com/repos/1781415302/fan-web/releases/latest`。
- Release tag 统一使用 `vX.Y.Z`。服务器和 App 共用同一个 tag，但独立判断自己的资产是否存在。
- Go 端版本变量是 `main.AppVersion`，源码默认值为 `dev`，正式构建通过 `-ldflags "-X main.AppVersion=vX.Y.Z"` 注入。`GET /api/version` 可查询运行版本。
- Flutter 端版本同时维护在 `mobile/pubspec.yaml` 的 `version: X.Y.Z+N` 和 `mobile/lib/widgets/user_sheet.dart` 的 `appVersion = 'X.Y.Z'`。`N` 是 Android `versionCode`，每次发布必须递增。
- 两端比较版本时去掉 `v` 前缀并按数字段比较，不使用普通字符串排序。

## 二、Release 资产契约

| 资产 | 用途 |
|---|---|
| `fan-web-server-linux-amd64` | Linux x86_64 服务器 |
| `fan-web-server-linux-arm64` | Linux ARM64 服务器 |
| `fan-web-server-darwin-arm64` | macOS Apple Silicon |
| `fan-web-server-windows-amd64.exe` | Windows x86_64 |
| `fan-web-app-vX.Y.Z.apk` | Android App |
| `SHA256SUMS.txt` | 4 个服务器二进制的 SHA256，不包含 APK |

一个 Release 可以只发布服务器端、只发布 App，或同时发布两端。提示规则必须保持独立：

- 服务器仅在最新 tag 更高且 Release 包含当前 `GOOS/GOARCH` 对应二进制时返回 `has_update=true`。
- App 仅在最新 tag 更高且 Release 包含 `fan-web-app-*.apk` 时提示更新。
- 因此，只有 APK 的 Release 不提示服务器更新；只有服务器资产的 Release 不提示 App 更新。

## 三、服务器端更新流程

管理员通过以下接口操作：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/update/check` | 查询最新 Release、版本、说明和当前平台资产 |
| POST | `/api/admin/update/perform` | 下载、校验、替换当前可执行文件并退出进程 |

`POST /api/admin/update/perform` 的固定流程：

1. 整个自更新过程由一把互斥锁串行化；已有更新进行中时，新请求立即返回「更新已在进行中」，不会阻塞等待（阻塞请求会随进程重启而连接断开）。
2. 重新读取 latest Release，并确认版本更高且当前平台资产存在。
3. **Windows 直接拒绝自动更新**：Windows 对正在运行的可执行文件加锁，无法改名替换，程序不下载即返回「Windows 平台暂不支持自动更新，请到 GitHub Releases 手动下载…」，引导用户手动替换。
4. 检查当前可执行文件所在目录可写，将新程序下载到同路径的 `.new` 文件（`O_EXCL` 创建；先清理上次中断可能残留的 `.new`）。
5. 若 GitHub 资产声明了大小，则要求下载文件大小完全一致。
6. 下载 Release 中的 `SHA256SUMS.txt`，从中精确匹配目标资产名，并校验新程序的 SHA256。
7. 将新程序设为 `0755`，把当前二进制改名为 `.old` 作为回滚备份，再把 `.new` 原子改名为当前程序路径；任一步失败均清理 `.new` 并尝试恢复旧程序。
8. **替换前若已存在 `.old`**（上一次更新的新版本未成功启动、未自动清理），拒绝覆盖并返回「检测到更新残留备份 …，请确认上一次更新已成功启动后手动删除再重试」，避免丢失唯一的回滚副本。
9. 替换成功后**刻意保留 `.old`**，不在此处删除——新版尚未启动，删除它会丧失回滚能力。HTTP 响应返回后当前进程退出，systemd 等外部进程管理器负责拉起新版本；没有进程管理器时由管理员手动重启。

更新校验采用失败关闭策略：校验响应最多读取 1 MiB；缺少校验文件、校验文件下载或解析失败、在读取范围内未找到目标资产摘要、摘要格式非法、摘要不匹配、资产大小不匹配，均取消替换并清理 `.new`。

### 回滚资产与自动清理

自更新引入一套完整的回滚资产，**只在新版本成功绑定端口后清理**：

- `<可执行文件>.old`：上一版本二进制回滚副本，由 `CleanupUpdateBackup` 在新版本成功绑定端口后删除。
- `<数据库>.pre-migration.bak`：升级前若有待执行的数据库迁移，会先对数据库做一致快照备份；由 `CleanupPreMigrationBackup` 在新版本成功绑定端口后删除。
- 任一次启动未能完成端口绑定，两者都保留，保证可完整回滚。

手动回滚步骤：停止新版进程 → 若存在 `<数据库>.pre-migration.bak`，覆盖回数据库并删除其 `-wal`/`-shm` 伴随文件 → 用 `<可执行文件>.old` 替换当前二进制 → 启动旧版本。该方案覆盖迁移提交之前与提交之后、端口绑定成功之前两类失败场景；新版一旦成功绑定端口，回滚资产即被自动清理。

## 四、Android App 更新流程

1. 用户在账号菜单主动点击“检查更新”，App 请求 latest Release。
2. 只有 tag 更新且 Release 中存在 APK 时，才显示版本号和 Release notes。
3. 用户确认后，dio 将 APK 下载为应用临时目录中的 `fan-web-update.apk`，界面展示下载进度并支持取消。
4. 下载完成后，`open_filex` 调起 Android 系统安装器，由用户确认安装。

App 不做后台更新、静默安装、强制更新或启动时自动下载。Android Manifest 声明 `REQUEST_INSTALL_PACKAGES`；APK 位于应用临时目录，不申请外部存储写权限。

## 五、发布流程

### 5.1 发布前

- 确定新 tag，确认未与现有 tag 冲突。
- 需要发布 App 时，同步 `pubspec.yaml` 的 `X.Y.Z+N` 与 `user_sheet.dart` 的 `appVersion`，并递增 `versionCode`。
- 按改动范围执行前端、后端和移动端测试；至少遵守 `AGENTS.md` 的 R3。
- 确认工作区不包含 `backend/web/dist/`、APK、签名文件或本地工具杂项等不应提交内容。

### 5.2 构建服务器资产（本次包含服务器端时）

1. 运行真实前端构建，并把 `frontend/dist` 嵌入 `backend/web/dist`。
2. 在真实前端仍位于 `backend/web/dist` 时，使用相同 `vX.Y.Z` 分别交叉编译 4 个服务器二进制。
3. 交叉编译完成前不得恢复被跟踪的占位 `backend/web/dist/index.html`，否则产物会嵌入“前端资源未构建”页面。
4. 检查 Linux AMD64 产物的 `-version` 输出，并确认二进制内不含占位页面、包含真实前端资产。
5. 对 4 个服务器二进制生成 `SHA256SUMS.txt`；不要把 APK 写入该文件。

### 5.3 构建 App 资产（本次包含 App 时）

- 正式 APK 必须使用 `mobile/android/app/fan-web-release.jks` 和 `mobile/android/key.properties` 配置的既有 release 签名。二者均为本地机密，不得提交或把内容写入文档。
- 缺少 `key.properties` 时 Gradle 会回退 debug 签名，这种 APK 只能用于本地测试，不能上传 Release。
- 构建后检查 APK 的 `versionName`、`versionCode` 和签名证书；版本必须对应 tag，证书不得是 Android Debug。
- 必须保管并异地备份原 keystore。丢失后无法用同一签名为现有用户提供原地升级。

### 5.4 发布与发布后检查

1. 确认待发布提交已推送，再创建并推送 tag。
2. 创建 GitHub Release，按本次实际改动上传服务器资产、APK 或两者；不要用缺失资产伪装全量发布。
3. 检查 Release 的 tag、标题、说明和资产名称，确认 GitHub Latest 指向新版本。
4. 抽查 `SHA256SUMS.txt` 与服务器二进制一致，验证服务器 `-version` 和真实前端嵌入状态。
5. 发布 App 时再次检查 APK 版本号、递增后的 `versionCode` 和 release 签名。
6. 按资产组合验证独立提示规则：服务器端只认匹配二进制，App 只认 APK。

发布过程中涉及的精确构建、校验、`gh release` 和事故恢复命令，统一使用 `.opencode/skills/publish-release/SKILL.md`，不要在其他文档复制并维护第二套命令。
